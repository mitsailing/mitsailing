10 list best practices (HTML/accessibility; this mock follows them)

  1. Use real list elements (ul, ol, li) for a collection of parallel items—the list is not decorative (“Semantics for lists,” WCAG Technique H48).
  2. Give the list an accessible name: associate it with a heading via aria-labelledby (here, the section’s Site alerts h2).
  3. If CSS removes bullets or you rely on flex/grid on the list, set role="list" on ul so assistive tech still exposes list length in browsers that suppress native list semantics.
  4. Keep a meaningful order (e.g. newest-first for alerts) and use the same order visually, in the DOM, and in any summary aria-label.
  5. Keep each item structurally parallel (same pieces in the same sequence—for example date, then title) so scanning and speech output stay predictable.
  6. Place supplementary navigation (e.g. “View all alerts”) after the list in reading order so context precedes the hub link (helps link purpose in context, WCAG 2.4.4).
  7. For dates, use <time datetime> with a visible label so machines and people both get a stable value.
  8. Do not nest extra interactive elements inside list items when the whole banner is already one link; keep dismiss outside the anchor to avoid nested controls.
  9. Truncate or clamp long titles in compact UIs; put the authoritative, untruncated wording on the detail or index page.
  10. Prefer ul for an unordered set; reserve ol when sequence, rank, or step number materially changes meaning.
